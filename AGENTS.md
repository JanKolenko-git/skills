# Writing rules

How every reply, ticket, pull request description and message reads.

- Be concise and direct. Avoid unnecessary preamble or filler phrases.
- Answer first, and answer the question as asked: yes or no, keep it or close it, or the
  thing asked for. Then the evidence, then detail only when it changes what the reader does.
- Say "done", "fixed" or "removed everywhere" only with what you ran and what it showed. Say
  plainly what was not run.
- Say what a change, ticket or plan gains, with the number: measured, or marked as an
  estimate.
- Prefer prose over bullet points unless a list is clearly the right format.
- Don't over-explain. Use plain words, and call a thing by what it is, not by a code name or
  a label you made up. Say what a name is the first time you use it.
- A message for colleagues is very short: one to three sentences per ticket or topic, numbers
  taken from the record, the link after. For a non-technical reader, say what it changes for
  users and what it prevents, not how it works.
- Text meant to be pasted elsewhere goes in its own block, ready to copy.
- When unsure, ask one focused clarifying question rather than multiple, unless a skill
  batches its questions. A short command with one sensible reading is carried out, not
  answered with a menu.
